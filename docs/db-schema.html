FacturaYa · modelo de datos

Supabase (Postgres). Salidas del agente: Pagar, Frenar, Escalar (PAY | HOLD | ESCALATE). Las reglas se escriben sobre vistas registradas en un catálogo, así que una fuente nueva no toca el código del motor.

  • Un archivo repetido no crea otra factura: file_sha256 es único.
  • decision_rule_hit guarda cada regla evaluada con lo observado y el límite, así la decisión se explica sin el LLM.
  • El motor decide una factura a la vez (pg_advisory_xact_lock), para que dos facturas no gasten el mismo saldo.

2Reglas y catálogo extensible

erDiagram
  RULE ||--|{ RULE_CONDITION : "AND"
  RULE_SOURCE ||--o{ RULE_CONDITION : "columna de"
  RULE_SOURCE ||--|| FACT_VIEW : "registra"
  RULE ||--o{ DECISION_RULE_HIT : "disparó"
  RULE_PROPOSAL |o--o| RULE : "al aceptar"
  RULE {
    uuid id PK
    text name
    text natural_language
    text effect "ALLOW ESCALATE HOLD"
    bool overridable
    text origin "HUMAN AGENT"
    text proposed_by
    timestamptz proposed_at
    text approved_by
    timestamptz approved_at "entra en vigor"
    bool active
    uuid replaces_rule_id FK
  }
  RULE_CONDITION {
    uuid rule_id FK
    text source FK
    text column_name
    text operator "EQ NEQ GT GTE LT IN BETWEEN IS_TRUE"
    jsonb value
  }
  RULE_SOURCE {
    text name PK "nombre de la vista"
    text label
    text description
    bool active
  }
  FACT_VIEW {
    uuid invoice_id "una fila por factura"
    any columnas "comentadas en español"
  }
  RULE_PROPOSAL {
    uuid id PK
    uuid operation_id FK
    text status "PENDING ACCEPTED REJECTED"
    jsonb conditions
    text rationale
    uuid_array evidence_invoice_ids
    uuid created_rule_id FK
  }
  • Vistas iniciales: fact_factura, fact_proveedor, fact_orden, fact_presupuesto (saldo global del mes). Las columnas se leen de information_schema, con su COMMENT ON COLUMN.
  • Un ALLOW solo cancela escalaciones de reglas overridable. Nunca cancela un Frenar ni el umbral de aprobación humana.
  • Un dato faltante siempre escala, nunca paga.

3Operaciones y costos

erDiagram
  OPERATION ||--o{ LLM_USAGE : "llamadas"
  OPERATION ||--o{ RULE_PROPOSAL : "propone"
  OPERATION ||--o{ APPROVAL : "revisó"
  INVOICE |o--o{ OPERATION : "procesada en"
  OPERATION {
    uuid id PK
    text type "PROCESS_INVOICE PROPOSE_RULES CHAT RULE_DRAFT"
    text status "RUNNING DONE FAILED"
    uuid invoice_id FK
    timestamptz started_at
    timestamptz finished_at
  }
  LLM_USAGE {
    uuid operation_id FK
    text purpose
    text model
    int input_tokens
    int output_tokens
    numeric cost_usd
    int latency_ms
  }
  • El botón "Proponer reglas" crea una operación PROPOSE_RULES. Un índice único impide dos corridas a la vez.
  • Al terminar bien, las 20 resoluciones revisadas quedan marcadas con reviewed_in_operation_id. Si falla, no se marca nada y se reintentan.
