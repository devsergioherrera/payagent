## Why this shape

- **One backend image, two commands.** `api` runs `uvicorn payagent.api.main:app`; `worker` runs `python -m payagent.worker.main`. Same code, same dependencies, so the engine cannot drift between them.
- **`domain/` has no imports outside the standard library.** That keeps invariant 2 of the spec (pure engine) enforceable: a test can import `domain/` and assert it never touches `adapters/`.
- **`src/` layout** avoids accidental imports of the backend folder as a package and makes `pytest` run against the installed package.
- **The worker and the API share two things:** Postgres and the `storage/` volume. Files uploaded through the API land in `storage/`, the worker reads them from there.
- **Live events (WebSockets).** The worker produces the events (`invoice.extracted`, `rule.evaluated`, ...) but the browser is connected to the API. Postgres `LISTEN/NOTIFY` bridges them without adding Redis: the worker does `NOTIFY`, the API listens and pushes to the open sockets.
- **SQL lives in `db/`, outside `backend/`,** so migrations and seed can be run by a script or pasted into the Supabase SQL editor.

## Deployment

```
                    ┌─────────────────── VM (Docker Compose) ───────────────────┐
 browser ──HTTPS──► │ caddy :443 ─┬─ /api/*, /ws/* ──► api :8000 ◄── NOTIFY ──┐  │
                    │             └─ everything else ► frontend :3000         │  │
                    │                                   worker ───────────────┘  │
                    │                                     │ IMAP/SMTP            │
                    └─────────────────────────────────────┼──────────────────────┘
                                                          ▼
                              Gmail          Supabase Postgres (DATABASE_URL)       Gemini API
```

**Target: one small Linux VM running `docker compose`** (Hetzner CX22, DigitalOcean 2 GB droplet, or GCP e2-small). Reasons it beats splitting across Vercel/Render:

1. The worker is a long-running process (IMAP every 10 s, cron). Serverless platforms kill it.
2. WebSockets need a persistent API process.
3. The spec requires `docker compose up` to bring up `api`, `worker` and `frontend`. On a VM, production is the same command plus an override file.
4. Caddy puts everything under one domain, so there is no CORS and the frontend calls relative `/api` and `/ws` URLs. It also gets the TLS certificate automatically.

**Domain:** a free subdomain is enough for the demo (`<ip>.sslip.io` or DuckDNS). Caddy issues the certificate for it.

**Steps:**
1. Create the VM, open ports 80 and 443, run `deploy/bootstrap-vm.sh`.
2. Copy `.env` to the VM (never committed).
3. `python scripts/migrate.py` once against Supabase.
4. `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build`.
5. Redeploy manually: `ssh vm 'cd hackathon && git pull && <step 4>'`. No CD pipeline (time limit).

**`.env.example` keys:** `DATABASE_URL`, `GEMINI_API_KEY`, `GMAIL_ADDRESS`, `GMAIL_APP_PASSWORD`, `APPROVER_EMAIL`, `PUBLIC_BASE_URL` (for the links in emails), `DOMAIN` (for Caddy).
